# Техническое задание: приложение «Статус»

**Версия:** 1.0 (черновик)
**Дата:** 29.07.2026
**Статус:** на согласовании

---

## 1. Общие сведения

### 1.1. Назначение
«Статус» — веб-приложение для формирования и мониторинга рейтинга продуктивности сотрудников. Сотрудники фиксируют выполненные рабочие действия, система рассчитывает баллы с учётом веса каждого действия и строит рейтинг и статистику за произвольные периоды (день / неделя / месяц / год / пользовательский интервал).

### 1.2. Термины
| Термин | Определение |
|---|---|
| **Параметр (действие)** | Стандартизированная единица работы, заданная руководителем для отдела (например, «подготовил материалы», «провёл встречу с клиентом») |
| **Вес (коэффициент)** | Множитель ценности параметра. Балл = вес × количество повторений |
| **Запись (лог)** | Факт фиксации сотрудником выполнения действия: параметр + количество + дата (+ комментарий) |
| **Рейтинг** | Ранжирование сотрудников отдела по сумме баллов за выбранный период |

## 2. Роли и права

| Возможность | Сотрудник | Руководитель |
|---|---|---|
| Вход в систему | ✔ | ✔ |
| Добавлять записи о своих действиях | ✔ | ✔ (для себя) |
| Просматривать свою статистику | ✔ | ✔ |
| Просматривать рейтинг отдела | ✔ (может быть ограничено настройкой) | ✔ |
| Управлять справочником параметров (CRUD, веса) | — | ✔ |
| Просматривать статистику по каждому сотруднику | — | ✔ |
| Корректировать/аннулировать записи сотрудников | — | ✔ (опционально, с логом изменений) |
| Управлять составом отдела и ролями | — | ✔ |

**Открытый вопрос для согласования:** требуется ли модерация записей (подтверждение руководителем перед начислением баллов) или записи начисляются сразу. В MVP — начисление сразу, модерация в backlog.

## 3. Функциональные требования

### 3.1. Аутентификация
- Регистрация/вход по email + пароль (в MVP — без SSO).
- Роль назначает руководитель при добавлении сотрудника в отдел.

### 3.2. Справочник параметров (руководитель)
- Параметр: название, описание (опционально), вес (десятичное число, по умолчанию 1.0), статус (активен/архив).
- Параметры привязаны к отделу; в MVP отдел один, но модель данных должна поддерживать несколько.
- Архивированный параметр не доступен для новых записей, но сохраняется в истории и статистике.

### 3.3. Фиксация действий (сотрудник)
- Экран «Мои действия»: таблица активных параметров отдела с кнопкой «+1» (быстрое добавление) и формой ввода произвольного количества.
- При добавлении: параметр, количество (целое ≥ 1), дата (по умолчанию сегодня, можно выбрать в прошлом), комментарий (опционально).
- Сотрудник может редактировать/удалять свои записи только за текущий день (ограничение настраивается).
- Запрет на записи «в будущее».

### 3.4. Расчёт баллов
- Баллы записи = вес параметра (актуальный на момент записи — вес фиксируется в записи снапшотом, чтобы изменение веса не переписывало историю).
- Сумма баллов сотрудника за период = Σ баллов его записей за период.

### 3.5. Рейтинг
- Таблица рейтинга отдела: место, сотрудник, сумма баллов, количество действий, динамика к прошлому аналогичному периоду (↑/↓, опционально в MVP).
- Фильтр периода: сегодня / неделя / месяц / квартал / год / произвольный диапазон дат.

### 3.6. Статистика
- Личная (сотрудник): график баллов по дням, разрез по параметрам (какие действия дают больше баллов), история записей.
- По отделу (руководитель): сводка по каждому сотруднику, топ параметров, активность по дням.
- Экспорт в CSV/Excel — backlog (в MVP не входит, заложить в API).

### 3.7. Аудит
- Все изменения записей руководителем логируются (кто, что, когда, старое/новое значение).

## 4. Нефункциональные требования

- Веб-приложение (SPA + PWA), адаптивная вёрстка (desktop + mobile), установка на устройство как отдельное «приложение» из браузера.
- Время отклика ключевых операций ≤ 1 с при нагрузке до 100 пользователей.
- Язык интерфейса: русский.
- Хранение данных: PostgreSQL.
- Разграничение доступа на уровне API, не только интерфейса.
- Развёртывание во внутреннем контуре компании без доступа к внешним облачным сервисам.

## 5. Стек технологий (согласован)

| Слой | Технология | Обоснование |
|---|---|---|
| Фреймворк | **Next.js (Pages Router) + TypeScript** — фронтенд и API (`pages/api/*`) в одном репозитории | Один фреймворк на всё; Pages Router — простой, стабильный, максимум примеров и документации |
| Стили | **Чистый CSS: CSS Modules + globals.css с CSS-переменными** | Без CSS-фреймворков; CSS Modules встроены в Next.js, изоляция классов без зависимостей |
| PWA | **next-pwa** | Установка «как приложение» на десктоп и мобильные устройства, кэширование |
| Работа с данными | **Нативный fetch** (без библиотек кэширования) | При микронагрузке слой кэширования не окупается |
| Графики | **Собственные SVG-компоненты** | Графики простые (столбики, линии); 0 КБ зависимостей, полная стилизация CSS. Если усложнятся — миграция на Recharts (SVG) без переделки данных |
| ORM | **Drizzle ORM** (+ Drizzle Studio для просмотра БД) | Лёгкая, TypeScript-нативная, схема в коде, простые миграции; проект подходящего размера для её освоения |
| БД | **PostgreSQL** | Стандарт для корпоративной ИТ-инфраструктуры (бэкапы, разграничение прав) |
| Аутентификация | **Auth.js**, провайдер Credentials (email/пароль); **интеграция AD/LDAP/SSO — backlog** | Не блокируем MVP; точка расширения закладывается в модель users |
| Деплой | **Docker Compose**: контейнер `next-app` + контейнер `postgres`, внутренний контур компании | Минимальные требования: любая виртуалка с Docker |

### Архитектурные правила
1. **Тонкие API-роуты:** вся бизнес-логика — в сервисном слое `src/server/`, роуты в `pages/api/` только валидируют вход и вызывают сервисы. Это сохраняет возможность переиспользования API, если в будущем появятся другие клиенты.
2. **Авторизация на уровне API:** проверка роли и прав — в каждом handler'е, независимо от того, что скрыто в интерфейсе.
3. **Репозиторий** — на корпоративном Git-контуре отдела, с README и инструкцией по деплою с первого коммита.
4. **Секреты** — только через переменные окружения (`.env` / корпоративный менеджер секретов), никогда в коде.

**Нагрузочный профиль:** десятки пользователей, единицы запросов в секунду — специальные меры производительности (кэш-слои, очереди, кластеры) не требуются. SSR не используется по назначению (внутреннее приложение за логином), страницы — клиентские компоненты с данными через API.

## 6. Структура приложения

### 6.1. Экраны (страницы)

| Маршрут | Экран | Роль | Содержимое |
|---|---|---|---|
| `/login` | Вход | все | Форма email + пароль |
| `/` | Мои действия | сотрудник, руководитель | Таблица активных параметров отдела: название, вес, кнопка «+1», кнопка «добавить количество» (диалог: количество, дата, комментарий) |
| `/history` | Моя история | сотрудник, руководитель | Список своих записей с фильтром по периоду; редактирование/удаление записей за текущий день |
| `/rating` | Рейтинг отдела | все (по настройке) | Таблица: место, ФИО, баллы, кол-во действий; фильтр периода (сегодня/неделя/месяц/квартал/год/диапазон) |
| `/stats` | Моя статистика | сотрудник, руководитель | SVG-график баллов по дням, разрез по параметрам (столбики), итоги за период |
| `/admin/parameters` | Параметры отдела | руководитель | CRUD справочника: название, описание, вес, архивирование |
| `/admin/employees` | Сотрудники | руководитель | Список отдела: добавление, роль, деактивация; сводка баллов по каждому за период |
| `/admin/entries` | Журнал записей | руководитель | Все записи отдела с фильтрами; корректировка/аннулирование (с записью в аудит) |

### 6.2. API-эндпоинты (`pages/api/`)

| Метод и путь | Назначение | Доступ |
|---|---|---|
| `POST /api/auth/*` | Вход/выход (Auth.js) | все |
| `GET /api/parameters` | Список активных параметров отдела | все |
| `POST /api/parameters` | Создать параметр | руководитель |
| `PATCH /api/parameters/:id` | Изменить параметр / архивировать | руководитель |
| `GET /api/entries?from=&to=&userId=` | Записи (свои или по отделу) | свои — все; чужие — руководитель |
| `POST /api/entries` | Добавить запись (параметр, кол-во, дата, комментарий) | все (для себя) |
| `PATCH /api/entries/:id` | Изменить запись | автор (текущий день), руководитель (любая, с аудитом) |
| `DELETE /api/entries/:id` | Удалить запись | автор (текущий день), руководитель (с аудитом) |
| `GET /api/rating?from=&to=` | Рейтинг отдела за период | все |
| `GET /api/stats/personal?from=&to=` | Личная статистика (по дням, по параметрам) | все (своя) |
| `GET /api/stats/department?from=&to=` | Сводка по отделу | руководитель |
| `GET /api/users` | Список сотрудников отдела | руководитель |
| `POST /api/users` | Добавить сотрудника | руководитель |
| `PATCH /api/users/:id` | Изменить роль / деактивировать | руководитель |

## 7. Модель данных (минимальная)

```
users        (id, email, password_hash, full_name, role, department_id, is_active)
departments  (id, name)
parameters   (id, department_id, name, description, weight, is_archived, created_at)
entries      (id, user_id, parameter_id, quantity, weight_snapshot, points, entry_date, comment, created_at, updated_at)
audit_log    (id, actor_id, entry_id, action, old_value, new_value, created_at)
```

`points = quantity × weight_snapshot` — считается при записи и хранится, чтобы статистика не пересчитывалась при смене веса.

## 8. План реализации MVP (оценка: 3–4 недели, 1 разработчик full-stack)

| Этап | Содержание | Срок |
|---|---|---|
| **0. Подготовка** | Согласование ТЗ (стек выбран: Next.js Pages Router + Drizzle + PostgreSQL, чистый CSS) | 1 день |
| **1. Каркас** | Репозиторий (Next.js + Drizzle + PostgreSQL), миграции, Auth.js (вход, роли), сид тестовых данных (1 отдел, 2 роли) | 3–4 дня |
| **2. Параметры** | CRUD справочника параметров для руководителя (название, вес, архив) | 2 дня |
| **3. Записи** | Экран сотрудника: таблица параметров с «+1», форма записи, история своих записей, удаление за текущий день | 3–4 дня |
| **4. Рейтинг и статистика** | Рейтинг отдела с фильтрами периодов, личная статистика (график по дням, разрез по параметрам), сводка руководителя | 4–5 дней |
| **5. Полировка и запуск** | Аудит-лог, валидации, обработка ошибок, Docker-сборка, деплой, тестирование на 5–10 пользователях | 3–4 дня |

### Критерии приёмки MVP
1. Руководитель создаёт параметр с весом — сотрудник видит его в таблице и добавляет «+1».
2. Рейтинг пересчитывается корректно при смене периода (день/месяц/год/диапазон).
3. Изменение веса параметра не меняет уже начисленные баллы.
4. Сотрудник не может видеть/менять чужие записи; руководитель — может, с записью в аудит.

### Backlog после MVP
- Интеграция с корпоративным AD/LDAP/SSO (после уточнения у ИТ наличия и условий).
- Модерация записей руководителем.
- Несколько отделов и кросс-рейтинги.
- Экспорт CSV/Excel, отчёты по расписанию.
- Уведомления (email), достижения/бейджи, цели по баллам.
- Динамика рейтинга (↑/↓), сравнение периодов.

## 9. Риски и открытые вопросы

1. **Честность самоотчётов** — баллы начисляются по декларации сотрудника; если это проблема, поднять приоритет модерации из backlog.
2. **Открытый вопрос:** виден ли рейтинг сотрудникам полностью или только своё место (влияет на мотивацию/демотивацию).
3. **Открытый вопрос:** нужен ли перенос незаполненных дней («нули») и нормативы (план баллов в день/неделю).
4. Список параметров пока не определён — первый шаг внедрения: руководитель отдела составляет 5–15 параметров с весами, система к этому готова.
